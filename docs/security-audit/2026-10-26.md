# mqtt-kit 安全審計

> 這是修復前的歷史快照。最新狀態請見 [修復結果](REMEDIATION_RESULT.md)。

審計日期：2026-10-26（Asia/Taipei）。範圍：工作目錄中的兩個 Rust crate、Cargo.lock、examples、tests、README、GitHub Actions。未修改產品程式碼或依賴，未建立 GitHub 倉庫或提交。

## 結論

目前不建議發布。發現 2 項高風險、2 項中風險問題，以及 CI 供應鏈防護建議。嚴重程度為此次審查對專案情境的判斷，不代表公告 CVSS 分數。

原有 29 項測試全部通過，但測試未涵蓋下列安全邊界。額外 4 項安全探針全部重現預期問題；探針通過代表「確認有問題」，不是「已修復」。

## 1. 高風險：TLS 依賴包含已公告的信任驗證問題

位置：Cargo.lock:1588、1644、2365；crates/mqtt-kit/src/builder.rs 的 tls_config()。

已下載最新 RustSec 資料庫（1,355 筆公告；擷取時 commit `8aaea89749881938068913df6911430bb2e3e41e`），cargo audit 回報 **11 筆漏洞版本命中，涉及 10 個不同公告 ID**，另有 2 筆資訊警告。不能將這些命中全部解讀成可直接利用的漏洞。

最需要優先處理的是實際 TLS 憑證驗證路徑：

- `rustls-webpki 0.103.13`：RUSTSEC-2026-0382。在信任錨允許建立相關憑證鏈時，可能接受已撤銷信任的 emSign 中繼金鑰；相關私鑰已公開。修補版本為 `0.103.16+`（0.103 分支）。
- `webpki-roots 1.0.9`：RUSTSEC-2026-0381。預設根憑證仍包含允許上述憑證鏈的根；修補版本為 `1.0.10+`。本專案未指定自訂 CA 時直接使用這個根憑證集合。
- `rustls 0.23.42`：另命中 4 個公告；建議升至 `0.23.46+`，並重新解析相容依賴。

攻擊者仍須具備相關憑證鏈、連線攔截等利用條件，並非所有 TLS 連線都可被任意偽造。

- `tokio 1.53.1`：RUSTSEC-2026-0386，AsyncFd 建構子違反 I/O safety；可升至 `1.53.3+`。本專案未直接使用這些 API，此次未證實可由遠端輸入觸發。
- `rustls-pemfile 2.2.0`：RUSTSEC-2025-0134，已停止維護；建議改用 rustls-pki-types 的 PEM API。停止維護本身不是已證實的可利用漏洞。

## 2. 高風險：Debug 輸出洩漏帳密與 mTLS 私鑰

位置：crates/mqtt-kit/src/builder.rs:12–19；crates/mqtt-kit-core/src/options.rs:66–71。

`MqttClientBuilder` 與 `TlsOptions` 使用衍生 Debug。`format!("{builder:?}")` 可直接取得密碼；TlsOptions 會將 client_auth 的完整私鑰以數字陣列輸出，可無損還原。應用若用 `tracing::debug!(?builder)` 記錄設定，敏感資料會進入日誌。

探針使用假密碼與假私鑰標記，已確認輸出包含敏感內容。Library 目前未主動記錄 builder；漏洞觸發條件是呼叫端記錄該型別，不代表此次已發生真實外洩。

建議手寫 Debug，對密碼及私鑰固定輸出遮蔽文字；巢狀 TlsOptions 也要獨立遮蔽。不要只修改日誌呼叫位置。

## 3. 中風險：明文 scheme 默默忽略 TLS 設定

位置：crates/mqtt-kit/src/builder.rs:208、324–343、359–378。

`.broker("mqtt://...").tls(...)` 仍回傳成功並使用明文 TCP；`ws://` 也忽略 TLS 設定，tls_client_config 同樣沒有明文 scheme 的衝突驗證。即使傳入無效 CA PEM，mqtt:// 仍能成功建立 client handle。

探針在 127.0.0.1 臨時埠接收 CONNECT 封包，確認第一個位元組為 MQTT CONNECT 的 0x10，且封包內能直接找到假密碼。這是 TLS 設定衝突未拒絕，不是 mqtts:// 被網路攻擊者自動降級。

API 註解有提到 tls() 僅於安全 scheme 生效，因此需要呼叫端設定錯誤才能觸發；但應以 fail-closed 避免「已設定 TLS」帶來錯誤安全預期。

建議只要 tls() 或 tls_client_config() 與 mqtt://、ws:// 同時出現，就回傳 InvalidConfig；未啟用 TLS feature 卻傳入 tls() 亦應明確拒絕。

## 4. 中風險：keep_alive 驗證不足，錯誤設定觸發 panic

位置：crates/mqtt-kit/src/builder.rs:221–223；crates/mqtt-kit/src/backend/mod.rs:241、265。

目前只拒絕零值，但 rumqttc 0.25.1 的 V3 路徑會對非零且小於 1 秒的 keep_alive panic，V5 路徑會對小於 5 秒的值 panic。探針分別用 V3 的 500ms 與 V5 的 1s 重現；connect() 未回傳預期的 InvalidConfig。

若設定來自外部輸入，可造成應用任務中止；程序是否退出取決於 panic 策略和呼叫方式。未證實惡意 broker 可直接觸發此設定問題。

建議依協定版本先驗證底層允許範圍，再建立 backend，加入回傳 Err 而非 panic 的回歸測試。

上游來源：https://docs.rs/rumqttc/0.25.1/src/rumqttc/v5/mod.rs.html 、https://docs.rs/rumqttc/0.25.1/src/rumqttc/lib.rs.html

## 其他防護建議

- CI 與 Release 的第三方 Actions 使用可變動的 tag／branch（包括 @master、@stable），未固定完整 commit SHA；Release job 擁有 contents:write，應優先固定該 job 的 Action 版本。這是供應鏈防護缺口，未發現已遭植入的證據。
- CI 未執行 RustSec 稽核，建議加入並對間接依賴的不可達命中設定有原因、有限期的例外。
- .gitignore 僅排除 target 與 .claude；可加入實際使用的 .env／私鑰／憑證檔案規則，避免重新加入 Git 追蹤時誤納。
